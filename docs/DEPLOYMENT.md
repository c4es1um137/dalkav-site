# Deployment

Cloudflare Pages builds and deploys from its GitHub integration. GitHub
Actions only verifies (no deploy job, no Cloudflare API token).

## Environments

| | Production | Test |
|---|---|---|
| Branch | `main` | `test` |
| Pages environment | Production | Preview (custom branch `test` only) |
| URL | https://www.dalkav.uk (apex 301 → www) | https://test.dalkav.uk |
| `SITE_ENV` (Pages variable) | `production` | `test` |
| Access | public | Cloudflare Access, owner's email only |
| Robots | indexable; `robots.txt` allows and lists the sitemap | `X-Robots-Tag: noindex, nofollow`, robots meta, `Disallow: /` |
| TEST banner and "[TEST]" title | no | yes |
| Drafts (`draft: true`) | excluded from pages, lists, RSS and sitemap | shown with a DRAFT / TASLAK pill |
| Lab variables | Production values | Preview values |

Everything that differs between environments comes from `SITE_ENV` through
one code path (`src/env.ts`): `_headers` (generated by
`src/integrations/env-files.ts`), `robots.txt`, the robots meta, the TEST
banner and title prefix, draft visibility, and the footer build info. There
are no per-environment files.

The build fails early if `SITE_ENV` is missing or invalid on Pages or CI, or
if it disagrees with the branch (`main` must be `production`; any other branch
must not be).

Locally, `SITE_ENV` defaults to `development`, which behaves like test.

## Build pipeline

`npm run build` runs, in order:

1. `astro check`: type errors fail the build.
2. `astro build`: content schema errors fail with the file path and field.
3. `node scripts/content-guard.mjs`: fails on private IPs, internal hostnames,
   denylist entries, image metadata, or raster images in `public/`. Prints
   `file:line RULE_ID` only. On production it lists every `[TODO` as a warning.
4. `node scripts/verify-dist.mjs`: checks links, metadata, hreflang, budgets
   (JS ≤ 5 KB gz site-wide, ≤ 3 KB per lab tool, CSS ≤ 35 KB gz), RSS,
   `_headers`, `robots.txt`, `_routes.json` and environment invariants. It
   prints the measured sizes.

CI (`.github/workflows/ci.yml`, job **verify**) runs the type check once, then
steps 2–4 for both `SITE_ENV=production` and `SITE_ENV=test`, on pull requests
to `main` and `test`, pushes to `test`, and on demand.

## Promotion (test → production)

1. Work on `test`, directly or through feature branches merged into `test`.
2. Check https://test.dalkav.uk.
3. Open a pull request with base `main` and compare `test`.
4. Wait for **verify** and the Cloudflare Pages check.
5. Merge with **Create a merge commit**. Squash and rebase are disabled because
   they make `test` and `main` diverge and cause repeat conflicts.
6. Production deploys from `main`.

`main` is protected: no direct pushes, PR required, no force push, no
deletion. `test` is protected against deletion and force push. **Automatically
delete head branches** must stay off, or merging the release PR deletes `test`.

A failed build never replaces the live deployment.

## Rollback

### 1. Instant, temporary (dashboard)

Cloudflare dashboard → **Workers & Pages** → `dalkav-site` → **Deployments**
→ pick a previous **Production** deployment → **⋯** → **Rollback to this
deployment**.

There's no rebuild, so it takes seconds. It lasts until the next push to `main`
deploys again. Use it to stop the bleeding, then do the permanent fix.

### 2. Permanent (GitHub)

1. On GitHub, open the merged release PR → **Revert** → this opens a revert
   PR into `main`.
2. Let **verify** pass, then merge the revert PR (merge commit).
3. Open a PR with base `test` and compare `main`, titled "sync after revert",
   and merge it, so `test` matches production again.
4. Fix forward on `test` and release as usual.

## Troubleshooting

Start with the build log of the failed deployment, the latest commits, and the
one component that changed. Never delete or recreate the Pages project or
domains, force-push, rewrite history, or change zone-wide settings without
asking first.

| Symptom | Likely cause | Check |
|---|---|---|
| Build fails: `SITE_ENV must be one of…` | Variable missing in the Pages environment | Pages → Settings → Variables and Secrets (Production *and* Preview) |
| Build fails: `Branch "main" must build with SITE_ENV=production` | Preview value set on Production or the reverse | Same place |
| Build fails: `InvalidContentEntryDataError` | Front matter doesn't match the schema | The error names the file and field; see `CONTENT.md` |
| `content-guard: FAILED … IPV4_PRIVATE` (or another rule) | An internal address or hostname in content | Open the named file and line; remove it. If it was already committed, stop and ask: it needs a history rewrite |
| `verify-dist: … broken internal href` | A link to a page that doesn't exist (often a typo in a slug) | The named page and link |
| test.dalkav.uk shows production content | The `test` CNAME targets `<project>.pages.dev` or isn't proxied | DNS → `test` record → target `test.<project>.pages.dev`, Proxied |
| test.dalkav.uk loads without login | Access application missing or wrong hostname | Zero Trust → Access → Applications |
| Pages build uses the wrong Node | `.nvmrc` missing or uses a codename | `.nvmrc` must contain a number (`24`) |
| CSP errors in the console on www only | Zone-wide Rocket Loader or Email Obfuscation injecting scripts | Add a hostname-scoped Configuration Rule that turns them off (see `SETUP.md` step 7) |
| `/api/lab/*` returns old values | Pages variables changed without a redeploy | Variables apply to new deployments: retry the latest deployment |
